Old unsafe route and cutover
- execution-reconciliation-engine/src/orchestration.ts selected FAILED_NOT_SUBMITTED at line 224
  and passed it through internal.ts persistOutcome to a raw IdempotencyRepository.recordOutcome.
  It could leave FAILED_NOT_SUBMITTED with an unresolved PENDING effect if used for recoverable orchestration.
- RecoverableOrchestrationRuntime instead accepts a narrow RecoverablePersistencePort and the
  PostgreSQL composer supplies only D4 boot, fenced pending writer, D3N terminal commit, and
  atomic adoption services. It does not inject IdempotencyRepository or call the legacy
  orchestrator. Lower-level APIs remain for other modes and infrastructure.
- Runtime dependency graph: broker adapter -> typed result/failure; D4 boot -> snapshot;
  fenced writer -> lease/recovery/pending/idempotency/outcome; D3N -> atomic terminal
  broker/pending/recovery/receipt closure; commit service -> canonical outcome adoption;
  reconciliation provider -> typed observation -> fenced writer.

Pre-I/O authority and transaction boundary
- A submission needs SANDBOX, matching adapter/request/pending identity and fingerprint,
  a nonterminal D4 intent classification, and ABSENT idempotency or an explicitly requested
  same-key retry from RETRY_AUTHORIZED. CLAIMED, SUBMITTED, unknown, terminal, and stale
  states cannot submit blindly.
- The fenced claim commits first. A separate fenced SUBMITTED write commits second. A
  further committed fenced check reauthorizes the current lease, revision, checkpoint,
  pending identity, and SUBMITTED state immediately before adapter invocation.
- The adapter is called only after those transactions end. Reconciliation similarly makes
  a committed fenced OUTCOME_UNKNOWN preflight before calling the provider. Returned facts
  are saved in a new fenced transaction. No transaction spans broker/provider I/O.
- Terminal boot returns TERMINAL_NON_SUBMISSION for submit, reconcile, and adoptAvailable
  without provider invocation.

Outcome routes
- Typed entry, protection, and cancellation acknowledgements/rejections are validated
  against request identity, persisted with the matching canonical transition and broker
  status, then offered to atomic adoption. No order ID, fill, timestamp, or rejection is
  synthesized. An already persisted canonical outcome can be adopted after reboot without
  calling the adapter again.
- A typed definite NOT_SUBMITTED, DO_NOT_RETRY adapter failure goes directly to
  commitNormalTerminalNonSubmissionDisposition. D3N atomically writes FAILED_NOT_SUBMITTED,
  terminal receipt, PENDING resolution, and terminal recovery ref. No split status write.
- Ambiguous failures and generic thrown ORDER_REJECTED become OUTCOME_UNKNOWN and require
  reconciliation. A frozen retry-safe definite non-submission may return RETRY_AUTHORIZED;
  the next submission requires an explicit same-key request and fresh authority.
- Reconciliation observations are persisted through the fenced writer. STILL_UNKNOWN
  remains blocked; CONFIRMED_NOT_SUBMITTED permits only explicit same-key retry;
  CONFIRMED_ACCEPTED and CONFIRMED_REJECTED without operation-specific canonical evidence
  return CANONICAL_OUTCOME_REQUIRED. A broker disposition is never adopted as canonical.

Crash boundaries covered on real PostgreSQL
- CLAIMED without SUBMITTED: intent disposition, no blind broker call.
- SUBMITTED before adapter call: reboot requires reconciliation, no second submission.
- Adapter call before outcome persistence: reboot requires reconciliation, no retry.
- Trusted definite non-submission: D3N closes the broker, pending, and recovery atomically.
- Canonical outcome committed but response lost: boot finds outcome; adoption converges
  without resubmission.
