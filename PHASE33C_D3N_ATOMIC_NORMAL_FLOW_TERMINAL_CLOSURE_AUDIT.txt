Public API and trusted proof
PostgresTerminalNonSubmissionCommitService now has separate public methods:
commitTerminalNonSubmissionDisposition remains the historical D3 method;
commitNormalTerminalNonSubmissionDisposition accepts a dedicated
NormalTerminalNonSubmissionRequest. The latter requires the full D1 logical
disposition, mandatory TerminalNonSubmissionProofV1 narrowed at the type level
to sourceKind=TRUSTED_ADAPTER_FAILURE, an explicit brokerStatusUpdatedAt, and
the existing owner/fence/revision/session/pending/broker authority. Runtime
validation rejects REVIEWED_LEGACY_ATTESTATION, malformed proof, retry-safe
failure, possible submission, wrong identity, and invalid chronology. The
caller must obtain the trusted typed failure after provider activity; this
persistence service creates no proof and performs no provider/broker I/O.

Normal transaction
1. Validate the D1 disposition/proof and explicit timestamp.
2. Start one physical transaction on the executor's pinned connection and
   verify exact D2C capability, database, schema, and search_path.
3. Read immutable receipt by ref, session, and exact broker triple before
   checking current broker status. Exact logical replay returns
   ALREADY_COMMITTED; conflicting replay returns RECEIPT_CONFLICT.
4. Lock/check lease at DB time; recheck receipt after lease serialization.
5. Lock recovery V1, validate revision/fence and frozen checkpoint, execution,
   mode, instrument, risk, and latest-R authority.
6. Lock exact pending PENDING row, validate null resolution fields, creation
   receipt, and execution checkpoint ancestry.
7. Lock exact broker row by adapter_id, environment, idempotency_key; require
   same operation/attempt/fingerprint, SUBMITTED, no adapterOrderId. Reject
   FAILED_NOT_SUBMITTED without receipt, OUTCOME_UNKNOWN, RETRY_AUTHORIZED,
   CONFIRMED, REJECTED, CLAIMED, or wrong identity.
8. Reject linked canonical and incompatible broker outcomes. Require proof
   observation at or after locked broker updatedAt and brokerStatusUpdatedAt
   at or after proof.observedAt. No wall-clock timestamp is generated.
9. Call recordIdempotencyOutcomeInTransaction on the SAME transaction with
   exact identity, FAILED_NOT_SUBMITTED, and brokerStatusUpdatedAt. Require
   APPLIED_TRANSITION with exact returned record and no adapterOrderId.
10. Insert immutable receipt containing the exact supplied proof, resolve
    pending TERMINAL_NON_SUBMISSION to the disposition ref at revision r+1
    and same fence, CAS recovery V2 to that ref/revision, verify all frozen
    authority, recheck lease at DB time, and commit.
Any pre-COMMIT failure rolls back the broker status, receipt, pending, and
recovery together. The lock order is lease, recovery, pending, broker, receipt
write. Receipt pre-reads are read-only.

Historical D3 and retries
Historical D3 still requires an already durable FAILED_NOT_SUBMITTED row,
PENDING effect, exact caller-supplied trusted D1 proof, and the existing
authority checks. It does not perform a broker transition. Normal and
historical fresh paths have mutually exclusive broker starting states.
After a successful normal COMMIT, a lost response retry reads the receipt
first and returns ALREADY_COMMITTED without a second broker transition,
receipt, pending resolution, or recovery advance. A changed logical proof
fails RECEIPT_CONFLICT. A no-receipt FAILED_NOT_SUBMITTED row is never normal
success.

Split-state and concurrency gates
The fenced writer's generic status method now excludes FAILED_NOT_SUBMITTED
at the type level and rejects it at runtime before any database I/O. D3N is
the orchestration persistence entry point for future normal terminal closure.
The lower-level execution idempotency repository remains a general domain
store; future C2B3 composition must route trusted normal terminal failures
through D3N, not make a split repository call. A deterministic real race
proves that when D3N owns the broker row, a direct legacy status writer blocks
on a distinct backend and returns DUPLICATE_SAME only after D3N commits.
Identical and conflicting D3N races pause A after its real lease row lock,
observe B's conflicting lease query on a distinct backend, and require the
observer's pg_blocking_pids(B_PID) to contain A_PID. Identical requests yield
COMMITTED/ALREADY_COMMITTED; conflicting proof yields COMMITTED/
RECEIPT_CONFLICT. Both leave one receipt, one terminal pending resolution,
one recovery revision advance, and one broker status transition.

Rollback, negative, and capability proof
Real tests inject failures before the broker update, after its update, after
receipt insertion, after pending resolution, after recovery CAS, at final
lease expiry, and immediately before COMMIT. Each proves durable broker
SUBMITTED, pending PENDING, no terminal receipt/ref, and unchanged recovery
revision. Negative tests cover every incompatible broker status; order ID;
adapter, environment, key, operation, attempt, and fingerprint mismatches;
reviewed, malformed, retry-safe, wrong-identity and chronologically invalid
proof; canonical acceptance/rejection, contradictory disposition; stale
fence, takeover, lease/recovery fence mismatch; and wrong database/schema.
The full D2C capability verifier runs on the same transaction connection.
