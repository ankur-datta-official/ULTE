PUBLIC CONTRACT AND TYPE BOUNDARY
@ulte/orchestration-state-store-postgres exports:
  interface PostgresSnapshotExecutor extends PostgresExecutor {
    snapshot<T>(work: (transaction: PostgresTransaction) => Promise<T>): Promise<T>;
  }
snapshot() is a required method. The ordinary PostgresExecutor interface is
unchanged. The compile-only contract test proves a plain PostgresExecutor is
not assignable to PostgresSnapshotExecutor, the latter still extends the
writer executor, and snapshot is required. No optional isolation argument,
caller-supplied isolation string, or executor cast supplies this capability.
Existing writer fakes remain plain PostgresExecutor implementations. The
separate execution-store-postgres PostgresExecutor remains unchanged; its
readIdempotencyInTransaction accepts the snapshot's query-capable transaction
structurally, as existing cross-package transaction-bound calls already do.
The migration coordinator's verifyTerminalSchemaCapabilityOnClient can use
the existing non-owning adapter pattern from terminal-commit-service:
query forwards to tx.query(sql, params ?? []), release is a no-op. No new
adapter or migration connection was introduced.

REAL EXECUTOR SEMANTICS
RealPostgresExecutor now implements PostgresSnapshotExecutor. snapshot() does:
1. pool.connect() once; bind and verify search_path on that client before BEGIN.
2. Fixed SQL: BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY.
3. SET LOCAL statement_timeout = 15000 and lock_timeout = 10000.
4. Probe pg_backend_pid() after isolation is established.
5. Invoke the callback with a transaction whose queries use that same client,
   including the existing bounded beforeQuery/afterQuery hook path.
6. COMMIT on success; ROLLBACK on callback/query/commit error; release client
   in finally. A rollback failure is paired with the original error.
No executor.query(), nested checkout, provider, or broker call occurs inside
snapshot(). The existing transaction(work) code remains BEGIN followed by
SET TRANSACTION ISOLATION LEVEL READ COMMITTED, its timeouts, callback,
COMMIT/ROLLBACK, and release. Snapshot neither consumes nor fires the
writer-only loseNextCommitResponse and failNextCommit flags.

REAL POSTGRESQL PROOFS
The dedicated tests/integration/d4s-postgres.test.ts ran against the disposable
ulte_b1f_test database and generated schema on PostgreSQL 18.6. Six tests pass:
* Server settings inside snapshot are repeatable read and read-only on;
  ordinary writer settings are read committed and read-only off. The writer
  successfully updates a row.
* PostgreSQL rejects INSERT and SELECT ... FOR UPDATE in snapshot with SQLSTATE
  25006. The rejected INSERT adds no row.
* Multiple callback reads report the same backend PID and verified generated
  schema/pg_catalog path. The source uses one pool checkout and pinned client.
* An explicit barrier holds B's snapshot after reading version 1. Distinct
  writer backend A commits version 2. B still reads version 1; a new snapshot
  reads version 2. This is not sleep-only synchronization.
* A callback error after a query invokes the rollback path; the pool has no
  checked-out client, and the same backend can be checked out afterward in
  read committed/read-write state. The disposable schema cleanup succeeds.
  The D4S test wrapper pairs any work and cleanup errors in AggregateError.
* A bounded query hook pauses an actual pinned callback query and is cleared
  safely. The checkpoint:load marker was added to the shared hook inventory.
* A snapshot leaves both writer fault flags armed. The following ordinary
  writer receives the synthetic lost-COMMIT response after a durable update;
  the following fail-COMMIT writer rolls back its update.
